# ISTe CS2 Tournaments

## Текущее состояние

Первый этап посвящён встраиванию турнирной системы в существующий сайт ISTe. Это отдельная подсистема, а не замена текущей страницы `/matches`, показывающей матчи команды из FACEIT.

Подтверждено при просмотре исходников:

- React 19, Vite 8 и React Router 7.
- Клиент Supabase используется для публичных данных, а основная сессия сайта хранится в защищённых HttpOnly cookies и обслуживается Vercel API.
- `src/auth/AuthContext.jsx` запрашивает `/api/auth/session` и хранит `user`, `role` и `isBlocked`.
- `src/auth/ProtectedRoute.jsx` ограничивает закрытые страницы.
- В `api/auth/login.js` проверяются `user_roles`, статус блокировки и дополнительная аутентификация для привилегированных ролей.
- Существующий маршрут `/matches` и его источники FACEIT не изменяем.

Полная проверка схемы действующей БД и правил RLS остаётся обязательной до применения миграций.

## Доступ и роли

Просмотр опубликованных турниров, команд, сеток и результатов общедоступен. Создание турнира, запись команды и отправка результатов требуют действующей сессии ISTe и незаблокированного аккаунта.

Организатор — не глобальная роль аккаунта, а владелец конкретного турнира. Он может назначать судей этого турнира. Организатор одного турнира не получает права редактирования другого. Администраторы ISTe могут модерировать турниры отдельно от прав владельцев.

Черновики доступны только владельцу и назначенным помощникам. Приватные и неопубликованные данные не включаются в публичные подписки Realtime.

Все разрешения на создание, изменение, судейство и подтверждение результатов проверяются на сервере. Ограничение кнопок через React не считается мерой безопасности.

## Два источника результатов

### Автоматический

Организатор размещает матч на выделенном сервере CS2, допускающем установку Metamod, CounterStrikeSharp и совместимого матчевого плагина. Предпочтительно оценить MatchZy, затем разработать адаптер ISTe Connect.

Плагин отправляет подписанные события по HTTPS в защищённый endpoint ISTe. Каждое событие содержит идентификатор сервера, матча, уникальный event ID, sequence, timestamp, тип события и нужную полезную нагрузку. Сервер проверяет подпись, срок действия, очередность, принадлежность матча и SteamID участников.

В хранилище записываются необработанные допустимые события и нормализованный счёт. Повторные event ID обрабатываются идемпотентно. При обрыве связи адаптер пытается восстановить передачу; интерфейс показывает устаревшие данные, но не выдаёт их за LIVE.

Подпись подтверждает, что сообщение пришло от привязанного сервера, но не гарантирует честность владельца чужого сервера. Официальные турниры ISTe требуют дополнительных процедур проверки.

### Без плагина

Организатор может указать адрес сервера для участников, но сайт не обещает автоматический LIVE счёт по одному IP адресу.

Капитан отправляет результат карты или серии с приложением доказательства. Второй капитан подтверждает его. При совпадении отчётов результат может быть принят в соответствии с правилами турнира. При конфликте создаётся спор и решение принимает уполномоченный судья. Все решения записываются в аудит.

Дополнительная клиентская телеметрия GSI, если будет добавлена, является недоверенной вспомогательной информацией и не заменяет подтверждённый результат.

## Модель данных (предварительная)

Префикс `tournament_` предотвращает конфликты с действующими сущностями сайта.

- `tournaments`: id, slug, owner_user_id, title, status, format, best_of, starts_at, published_at, rules, created_at.
- `tournament_staff`: tournament_id, user_id, role (judge/manager).
- `tournament_teams`: id, tournament_id, name, captain_user_id, status.
- `tournament_team_members`: team_id, user_id, steam_id, roster_state.
- `tournament_entries`: tournament_id, team_id, seed, registration_state.
- `tournament_matches`: id, tournament_id, stage, round_index, slot_index, team_a_id, team_b_id, best_of, status, winner_team_id, version.
- `tournament_match_maps`: id, match_id, map_name, map_index, score_a, score_b, status.
- `tournament_match_reports`: id, match_id, reporting_user_id, proposed_result, evidence_reference, state.
- `tournament_match_events`: id, match_id, server_id, external_event_id, sequence, payload, received_at.
- `tournament_servers`: id, owner_user_id, title, connection_state, last_seen_at.
- `tournament_server_credentials`: server_id, key_identifier, hashed_or_encrypted_secret, revoked_at.
- `tournament_audit_events`: actor_user_id, tournament_id, match_id, action, before_state, after_state, created_at.

Ссылки на пользователей должны соответствовать фактической схеме авторизации ISTe. Для результатов матчей необходимы транзакции, optimistic versioning и блокировка от параллельного принятия несовместимых результатов. Секреты недоступны клиенту и публичным запросам.

## Жизненный цикл матча

`scheduled → live → pending_verification → completed`

При споре `pending_verification → disputed`, после судейского решения `disputed → completed`. Отмена и техническое поражение задаются отдельными серверными переходами.

Только подтверждённый `completed` может определить победителя серии и передать его в следующую встречу. Переход и фиксация результата должны происходить в одной транзакции. Исправление завершённого матча, если последующая игра уже началась, требует ручного разрешения конфликта, а не тихой перезаписи сетки.

Для первой версии: Single Elimination, 2–64 команды, автоматические BYE, BO1 и BO3, публикация, заявки и ручная проверка результатов.

## API (контракт на этапе проектирования)

- `GET /api/tournaments` — публичный список опубликованных турниров.
- `GET /api/tournaments/:id` — публичные сведения и сетка с учётом статуса.
- `POST /api/tournaments` — черновик от авторизованного пользователя.
- `POST /api/tournaments/:id/publish` — публикация владельцем.
- `POST /api/tournaments/:id/entries` — заявка команды.
- `POST /api/tournament-matches/:id/reports` — отправка результата капитаном.
- `POST /api/tournament-matches/:id/confirm` — подтверждение другой стороной.
- `POST /api/tournament-matches/:id/resolve` — решение назначенного судьи.
- `POST /api/tournament-servers/pair` — краткоживущий код привязки сервера.
- `POST /api/tournament-events/ingest` — подписанные события серверного плагина.

Маршруты контрактные, ещё не реализованы. Перед реализацией изучить существующие `api/lib` и `server/lib` для единых guard, cookie session, rate limit и audit. Не копировать секреты в клиентский код.

## Этапы работ

1. Проверить актуальные миграции, таблицы пользователей, RLS, API guards и маршруты. Утвердить модель доступа и SQL миграции.
2. Реализовать публичный каталог, создание черновиков и управление своими турнирами на существующей авторизации.
3. Реализовать Single Elimination с BYE, BO1/BO3, подтверждаемым ручным счётом и тестами конкурентных обновлений.
4. Сделать тестовый сервер CS2, установить совместимые плагины и проверить реальные игровые события и восстановление после разрыва связи.
5. Создать безопасную привязку серверов, приём событий и LIVE подписки; затем обработку споров и расширенную статистику.

## Условия выпуска

- Гость видит только опубликованные турниры и результаты.
- Незалогиненный и заблокированный пользователь не может создавать турниры даже прямым вызовом API.
- Пользователь не может изменять чужой турнир.
- Победитель продвигается один раз после подтверждения результата.
- Повторный webhook не меняет итог второй раз.
- Ручной режим не показывает фиктивную игровую телеметрию.
- Потеря соединения плагина не обнуляет последний достоверный результат.
- Ошибочные и спорные результаты имеют прозрачный журнал исправлений.
- Регрессия текущих страниц ISTe, входа и FACEIT статистики отсутствует.
- До релиза обязательны lint, build, тесты прав доступа и ручной сценарий с двумя командами.

Этот документ фиксирует архитектуру; ни миграции production базы, ни подключение игровых серверов им не выполняются.
